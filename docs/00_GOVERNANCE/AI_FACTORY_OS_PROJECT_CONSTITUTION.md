## 1. Project Mission

Build a **modular AI business operating system** that can:

- Identify product opportunities
- Produce digital product assets (Content Factory)
- Support human-assisted publish and market validation
- Learn from execution and commercial feedback
- Remain governable as complexity grows
- Preserve independent module value while enabling governed composition

Mission is **commercial validation capacity under control**, not uncontrolled automation.

---

## 2. Long-Term Direction

**Product direction:** Modular AI Business Operating System（模块化 AI 商业操作系统）.

```
Data → Cognition → Decision → Execution Runtime → Content Factory
  → Commercial Assets → Feedback → Memory Learning
```

Long-term target: compose independent capability modules under **unified governance, data boundaries, contracts, and orchestration** — **without** requiring forced code merge into a single Runtime, and **without** destroying Pilot traceability or Human Assisted boundaries.

Near-term discipline: **Governance Before Expansion**.

See **Modular Capability Principle** below and **DEC-013**.

## Autonomous Commercial Learning Principle

> Entry **049** / **DEC-020**；050–062：… / Acquisition Engine / **Search Origin & Missing Fields**；**2026-09-04 / DEC-033** 商业结果优先与成本/职责/解耦硬化。

AI_FACTORY_OS 的商业能力应逐步形成持续商业学习闭环：

```text
市场/数据采集 → Opportunity Discovery → 机会评分 → 受控选品
  → 实验 → 生产 → 质量/商业/风险门控 → Publish Queue
  → 真实市场观察 → Feedback → Evaluation → Memory/Learning
  → Strategy Update → 下一轮机会发现
```

**目标方向：** 在明确规则与风险边界内，系统逐步自主完成低风险商业决策与循环学习。  
**不是：** 要求用户对每一个产品做手工商业审批。

### Commercial Outcome Primacy（DEC-033）

> **赚钱是最高商业目的** — 形成真实、可持续、可验证的商业回报。

优先级（不可颠倒）：

```text
可销售质量底线
        ↓
真实商业结果
        ↓
单位经济性 / 成本效率
        ↓
自动化与系统完善度
```

- 系统完整性、自动化程度、AI 使用程度、架构复杂度、技术先进程度 **不得** 凌驾于商业结果。  
- **不等于** 为赚钱牺牲可销售质量、真实性、合规或治理。  
- 「赚钱第一」≠「已经赚钱」；原则固化 ≠ 收入已实现。

### Lowest Reasonable Cost & AI Cost Discipline（DEC-033）

> **最低成本达到可销售质量，而不是最低成本制造垃圾产品。**

成本判断必须包含：人工 / 计算 / 存储，以及 **AI 调用成本 / 模型推理成本 / 重复生成成本**。

- AI 不是默认越多越好；自动化不是默认越多越好。  
- 高成本 AI 调用不能仅因「更智能」自动获得优先级。  
- 能由规则、代码、模板、缓存、已有资产、批处理、复用解决的，优先低成本方案。  
- 只有当额外 AI / 自动化成本具有合理商业回报时，才应增加。  
- 产品选择必须考虑单位经济性，而不是只看需求热度。  
- 生产策略须考虑：售价 / 可预期收益 / 生产成本 / AI 边际成本 / 可复用程度。

**一次生产、多次复用：**

```text
一次生产 → 质量验证 → 资产复用
  → 多次销售 / 多平台销售 / 多种商业化
  → 市场反馈 → 必要时低成本迭代
```

优化目标不是「每一次都重新调用高成本 AI」。

### Human Gate Boundary（人工闸门边界）

```text
AI Autonomous Decision Layer
        ↓
Risk Classification
        ↓
Low Risk → system may continue automatically（在授权规则内）
High Risk / External Irreversible Action → Human Gate
```

人工 Gate **负责控制**：平台账号风险、不可逆外部操作、付款、广告、（当前阶段）真实发布动作。  
人工 Gate **不负责**：替 AI 做所有商业判断、把系统退化成「每生产一个产品就人工批准」。

### User Responsibility & Autonomous Operation（DEC-033）

> **正常情况下自主运行；重大异常才需要用户介入。**

```text
系统（正常）：
市场采集 → 机会发现 → 选品 → 实验 → 生产
  → 质量检查 → 成本检查 → 商业风险检查 → 优化 → 成品准备

用户（正常）：
最终成品发布（不可逆外部动作）
```

用户 **不是** 系统日常商业决策员，也 **不是** 技术执行员。  
用户不承担：技术 Reality 验证、Git 操作、Audit 编写、日常技术决策、每个产品的中间审批、每一步生产确认、每个实验的手工商业批准。

用户在 **重大异常** 时介入，包括但不限于：产品质量明显低于预期；过于单调/重复；长期销量低；生产成本过高；AI 成本失控；明显偏离赚钱主线；产品方向重大错误；合规/平台等重大风险。

**Human External Action Gate（DEC-023）仍然有效：** 用户负责最终不可逆外部动作 ≠ 用户审批系统内部每个商业步骤。

## Core Documentation Continuity Rule

AI_FACTORY_OS 的项目连续性**不能**依赖 Conversation Memory。

### Current Core Continuity Domain

`docs/0–6`（`00_GOVERNANCE` → `06_HISTORY`）是当前项目的**核心连续性记录域**。  
未来任何新的 AI 会话、项目恢复、ZIP 恢复、重大任务规划，都应能够通过 `docs/0–6` 恢复：项目规则、当前状态、商业状态、架构状态、执行进度、重要决策与长期演进背景。

### docs/0–6 责任边界（Information Ownership）

| 目录 | 负责 | 不负责 |

## Modular Capability Principle

AI_FACTORY_OS consists of **governable capability modules**（由可治理能力模块组成）.

每个模块可以：

* **独立演进**（independent evolution）
* **组合使用**（compose with other modules）
* **形成解决方案**（form solutions）

并保持：

* independent capability value
* independent commercialization possibility

Modules may operate independently or combine through governance and orchestration into a complete AI business operating system.

**边界（必须保留）：**

| 正确 | 禁止误解 |
|------|----------|
| 模块化（Modular） | ≠ 碎片化（Fragmented）— 无契约、无治理的散装 |
| 统一治理（Unified governance） | ≠ 强制融合（Forced Merge）— 强制单 Runtime / 消除独立模块 |

**「统一系统」不得被理解为：**

* 所有模块必须代码融合
* 所有能力必须进入单一 Runtime
* 独立模块必须被消除

**历史目录背景：** 见 [ARCHITECTURE_EVOLUTION_CONTEXT_RECORD](../06_HISTORY/AI_FACTORY_OS_ARCHITECTURE_EVOLUTION_CONTEXT_RECORD.md)（解释层，非状态权威）。

## Capability Composition Principle

> Entry **041-B-B** / **DEC-014**。与 Modular Capability Principle（DEC-013）互补；不改变 Current Reality。

AI_FACTORY_OS **不以目录作为商业边界**。

- **目录（Folder）** 主要用于工程组织（0–11 等）。
- **真正商业价值** 来自 **Capability（能力）**，而非文件夹名称。

Capability 可以：

- 独立运行
- 独立演进
- 独立商业化
- 与其他 Capability 组合形成 Solution

**明确等式 / 不等式：**

| 表述 | 含义 |
|------|------|
| **Module ≠ Folder** | 模块是能力边界，不是目录本身 |
| **Capability ≠ Implementation** | 能力是可治理的价值单元；实现可跨目录、可演进 |
| **Product = Capability Composition** | 产品来自能力组合（或单能力包装），不是「某个文件夹=产品」 |

**统一治理 ≠ 强制融合 Runtime。** 目标是可治理、可组合、可商业化的能力体系——**不是**把所有能力强制塞进单一 Runtime。

See **DEC-014**.

## Information Ownership Principle

> Entry **041-F** / **DEC-016**。

每类信息必须有**唯一最高权威归属**。  
其他文件可以**引用**，**不得重复定义**（避免 AI 误判冲突来源）。
